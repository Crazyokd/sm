# Agent 开发规则

## 测试脚本开发与评审

新增、修改或评审测试脚本前，必须先完整阅读
[`docs/assert_rules.md`](docs/assert_rules.md)，并将其作为测试实现的验收门槛。仅通过语法检查、
`pytest --collect-only` 或测试当前运行通过，不能证明测试逻辑正确。

开发和评审测试脚本时必须完成以下检查：

1. 根据测试用例、协议定义或需求确认前置条件、操作步骤、输入数据和预期结果；不得根据被测系统的实际输出反推预期值。
2. 逐项确认用例要求的操作确实执行，辅助方法的返回值和异常没有被忽略，并检查同类能力是否已有公共 fixture、client 或 helper 可复用。
3. 对写操作、任务和异步状态变化，验证“前置状态 -> 本次操作 -> 状态迁移 -> 最终结果”的完整因果链，排除历史残留状态导致的假通过。
4. 同时检查 Modbus 通道、功能码、从站、寄存器或线圈地址和字段含义，确保断言验证的是本次操作对应的正确对象。
5. 确认失败路径仍会执行恢复、停止、取消或数据还原；涉及机器人运动的测试必须具备失败安全措施。
6. 给出至少一个具体反例：删除被测操作、返回错误状态或读取到旧状态时，测试必须失败。无法说明失败条件的断言不得合入。

提交测试脚本的 MR 时，必须填写默认 MR 模板中的测试脚本检查项。不适用的项目需写明原因，
不得仅以静态检查或用例收集结果代替断言有效性评审。

## Git 开发流程

每次开始开发前必须执行以下流程：

1. 检查工作区状态，保留并识别用户已有改动，不得擅自覆盖或删除。
2. 获取远端最新代码，将本地主分支以 fast-forward 方式更新到 `origin/main`。
3. 从最新主分支创建新的开发分支，禁止直接在主分支上开发。

参考命令：

```bash
git status --short --branch
git fetch origin --prune
git switch main
git pull --ff-only origin main
git switch -c <开发分支>
```

开发完成后必须：

1. 执行与改动范围匹配的验证，并记录验证结果。
2. 只暂存本次改动，不得提交无关文件、凭证、运行产物或 IDE 配置。
3. 提交代码并推送开发分支到远端。
4. 创建目标分支为 `main` 的 Merge Request。

## MR 标题

MR 标题必须使用中文，并使用以下格式之一：

```text
fix: 修复内容
feat: 功能内容
```

- 修复缺陷使用 `fix:`。
- 新增功能、测试能力或自动化覆盖使用 `feat:`。
- 冒号后保留一个空格，标题正文使用中文。

## MR 描述

MR 描述必须使用中文 Markdown，并至少包含以下内容：

```markdown
## 改动范围

- 说明修改的模块、文件或功能。

## 改动原因

- 说明问题背景和修改目的。

## 影响范围

- 说明对现有功能、兼容性、运行环境或测试资源的影响。

## 验证结果

- 列出实际执行的验证命令及结果。
- 未执行的硬件、集成或破坏性验证必须明确说明原因。
```

MR 描述不得只写“已修改”或“测试通过”，必须提供可复核的改动和验证信息。
