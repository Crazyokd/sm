# /ones:bugfix — 从 ONES 问题分析到 MR 提交的完整闭环

对 ONES 现场问题执行完整闭环：**问题分析 → 报告上传 → 代码修复 → 测试验证 → MR 提交**。

## 参数

$ARGUMENTS

- 第一个参数：ONES 工作项 ID（序号）
- `--skip-analysis`：跳过分析阶段（已有分析结论时）
- `--skip-upload`：不上传报告到 ONES

---

## Phase 1：问题分析与报告上传

调用 `/ones:analyze <ID>` 完成双 Agent 独立分析。

分析完成后**立即上传报告到 ONES**（不等修复完成），确保分析结论尽早可见。

---

## Phase 2：代码修复

### 2.1 创建分支

```bash
git checkout -b fix/<简短描述> main
```

### 2.2 修复原则

- **最小化变更**：只改必须改的，不搭车重构
- **核心修复 + 防御性保护**：先修根因，再在关键调用节点加参数校验
- **保持现有代码风格**

### 2.3 编写单元测试

测试文件与被测文件同目录，命名 `<模块>_test.cpp`。

**必须覆盖**：
1. **回归测试**：精确复现问题触发条件
2. **边界值**：0、负数、极大值
3. **正常值**：验证修复不破坏已有逻辑

---

## Phase 3：编译与测试验证

在 Docker 编译容器内完成编译和测试运行，确保全部通过。

---

## Phase 4：提交与 MR

### 提交信息格式

```
#<ONES_ID> fix(<scope>): <一句话描述>
```

### MR 描述要点

MR 描述的目标是让 reviewer **无需逐行看代码就能理解 why/what/how**：

1. **Summary**：ONES 链接、影响范围（量化）、引入提交
2. **Root Cause**：用旧版本 vs 新版本的代码对比 + 数值推导展示 bug 成因
3. **Changes**：逐文件说明改了什么、为什么这么改
4. **Test plan**：已完成和待完成的验证项

---

## 流程检查清单

- [ ] 分析：根因明确，证据链完整
- [ ] 报告：已上传到 ONES
- [ ] 修复：核心修复 + 防御性保护，最小变更
- [ ] 测试：回归 + 边界 + 正常值，全部 PASSED
- [ ] 编译：容器内通过
- [ ] MR：描述含根因对比、数值推导、变更说明
- [ ] ONES 回写：如有状态流转，transit 后用 `tasks/update` 把 `assign` 与 `HiRJZNR7`（问题解决人）回写为 ONES token 用户 UUID（详见 common.md「默认负责人 / 问题解决人」）
