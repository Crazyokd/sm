# 分析

日志、截图和代码搜索结合的问题分析，走这个流程。

## 默认模式

默认做一次深入的本地分析。

除非用户明确要求委派或并行 agent，否则不要启用 sub-agent。若用户明确要求，可以做两轮独立分析再合并。

## 工作目录

使用 `/tmp/ones-analyze/<ID>/`，子目录包括：

- `images/`
- `sros-logs/`
- `allspark-logs/`
- `other-logs/`

## 流程

1. 先读 [common.md](./common.md)
2. 获取 task info、members、types、statuses、fields、sprints、attachments
3. 总结问题描述
4. 如果没有日志或没有可用附件，就评论说明分析受阻并结束
5. 只下载和预处理真正有用的附件
6. 提取业务关键词、技术关键词和时间范围线索
7. 精确搜索代码和日志，不要把整包日志直接灌进上下文
8. 输出带证据标记的根因报告

## 证据规则

- 每个结论都标记为直接证据或推理结论
- ONES 里已有的“原因分析”文本不能直接当证据
- 证据优先级上，日志高于纯代码猜测

## 报告结构

最终报告至少覆盖：

1. 根因
2. 因果链
3. 时间线
4. 证据
5. 分析过程
6. 影响范围
7. 修复建议
8. 关键代码路径

如果要把报告回写到 ONES，前面加上 [common.md](./common.md) 里的 HTML AI 声明。

回写到 ONES 描述/问题详情时只能追加：先读取当前 `desc_rich`，在原内容后追加分隔线、HTML AI 声明和分析报告；禁止用分析报告覆盖原有问题详情。无法安全追加时，改用评论 `send_message`。
