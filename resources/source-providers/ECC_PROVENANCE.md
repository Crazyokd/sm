# ECC file provenance

The explicit source selection preserves 488 existing legacy resource paths without vendoring upstream bodies. Each file was verified against its ECC 2.2.1 native installation record (`~/.claude/ecc/install-state.json`) and the original published package bytes. This includes 202 runtime files under `.claude/scripts`, retained together as the internal `ecc-runtime` supporting-files dependency. The dependency is referenced by complete functional resources and is not a public resource type or independent optimization target.

ECC is one shared upstream fetch in the catalog's named source registry. Its complete functional members have independent resource identities, scopes, status and proposal selections. Supporting files render with their actual consumers, inheriting each consumer scope; matching shared file ownership retains them until the last consumer is removed. The generator writes directly to intended target-relative paths, including legacy client mirrors. Complete Skill trees follow additions and removals in the generated source; a missing selected member leaves only that resource unavailable. Unsafe or malformed sources remain hard failures.

Ten old rule aliases remain symlinks and derive ownership from their canonical rule targets without duplicate file claims. Locally adapted or unverified files remain separately declared self-maintained resources with their provenance retained. Each self-maintained native configuration fragment is stored as a JSON object in its own resource directory and merged into the native JSON/TOML target; private values stay local.

Native generation against published ECC 2.2.3 produced 1,066 unique targets. All 488 extra files matched the published archive bytes, SHA-256 values and executable flags. The new generator reproduced all 1,066 target bytes and executable flags exactly in a temporary directory. No selected published source was missing in that validation, and no resource-defined business workflow was executed.

The independent-resource handoff was checked with a copied SQLite state and the actual filesystem. It preserves installed file bytes and executable flags, native configuration values and array order. This is development-side conversion evidence. Local deployment and upstream refresh acceptance are recorded separately in the delivery MR.


The runtime dependency has 43 verified consumers: 28 Hooks, seven Skills, seven prompts and one Agent. Existing native Hook commands reference bootstrap/runner modules; command and Skill bodies reference update, audit, package-manager, health and worktree-orchestration utilities. The companion `orchestration-status.js` is documented by the cached approved ECC 2.2.1 `docs/zh-CN/commands/orchestrate.md` and belongs to that same orchestration capability. Keeping the full approved runtime module set preserves its installed libraries and type declarations without creating standalone implementation-file resources.

The complete-unit conversion preserves all 202 runtime target bytes and executable flags. Reviewed adoption transfers each old implementation-file owner to a named real consumer, then explicitly names that first consumer for additional identical shared claims. No installed file, native setting, credential, trust state or live ownership database is written by the conversion.
