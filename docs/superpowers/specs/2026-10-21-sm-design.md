# SM 第一阶段需求与行为约定

状态：已确认；实现期间按用户澄清补充 Skill 的客户端无关性。

## 1. 要解决的问题

AI 资源散落在不同的用户目录、项目和工具配置中，来源、归属和维护方式不清楚。日常修改难以统一管理，换机器时也缺少明确的恢复步骤，导致 Agent 的能力和使用体验下降。

SM 要提供可视化管理、统一维护流程和本地初始化能力，使同一用户能在多台机器上恢复资源，并根据真实使用情况持续改进自建资源。

## 2. 使用环境与协作边界

- 第一阶段面向 Linux，接入 Codex 和 Kimi，按本地使用场景设计。
- 主要服务同一个用户的多台机器。各台机器采用相同的工作目录名、项目命名和组织结构。
- 其他人可以使用同一流程，但必须遵循相同的目录约定。
- 协作沿用 GitLab：提交 MR、人工审核合并、各个本地环境定时拉取并应用。
- 第一阶段维护一份当前内容，以主分支为唯一维护来源。不增加多版本选择、并存、发布通道或产品层面的分支管理。
- 作用域只考虑用户级和项目级。

## 3. 管理对象与独立维度

第一阶段纳入五类资源：

| 资源类型 | 管理内容 |
| --- | --- |
| Skill | 使用说明、触发描述、执行流程，以及随附脚本和资源 |
| Hook | 触发条件、自定义行为、执行脚本和生效配置 |
| 规则文件 | 用户或项目的长期约定，例如 AGENTS.md |
| Agent 定义 | 角色说明及相应配置 |
| MCP 配置 | 工具连接及所需的配置声明 |

分类采用多个独立维度，不把不同维度混成互斥目录：

| 维度 | 分类或归属 |
| --- | --- |
| 资源类型 | Skill、Hook、规则文件、Agent 定义、MCP 配置 |
| 创建方式／来源 | 用户自建、上游拉取 |
| 作用域 | 用户级、项目级；项目级声明具体的项目归属 |
| 客户端适配 | 仅用于依赖原生格式的资源；Skill 本体不按客户端分类 |

用户级资源在对应用户与 Agent 的范围内使用。项目级资源在声明归属的项目中使用，不扩大到用户级。多台机器根据同一份作用域信息和目录约定确定应用位置。

不同资源类型、不同 Agent 的格式和生效方式分别处理，不假定它们拥有完全相同的能力。

Skill 只有一份内容定义和一个内容入口，不区分 Codex、Kimi 或其他客户端。客户端发现位置、加载与采集属于适配层，不进入 Skill 的内容分类。第一阶段使用 Codex、Kimi 均支持的 `.agents/skills/` 共享目录，不生成两份客户端副本。

## 4. 维护内容与本地生效位置

自建资源统一保存在 SM 仓库，通过 SM 的 MR 维护。用户目录和各项目目录是应用位置，作用域不决定资源必须分散在哪个仓库维护。

日常创建、编辑、组织调整和淘汰所修改的是 SM 中的待审核内容。实际生效位置由同步应用流程更新。

重命名、移动、重新归类和调整项目归属属于正常管理操作。应用合并后的调整时，应同步处理受管理的旧位置，避免旧副本继续生效；不清理无关的本地内容。

上游资源登记来源、作用域和适用 Agent，从其上游获取内容。自建和上游的维护责任、更新路径分别保留。

## 5. 两类资源的更新路径

### 自建资源

用户主动修改与 AI 提出的优化采用相同流程：

创建或修改 → 提交 MR → 人工审核合并 → 下一次本地拉取并应用 → 生效。

待审核的改动不能直接应用到本地运行环境。审核合并后，各台机器按既定节奏获取当前内容并应用。

### 上游资源

本地定时直接跟随上游，并按声明的作用域应用，不为普通上游更新增加 SM 的 MR 审核。

上游资源不进入自建资源的夜间反思与优化流程，不生成针对上游 Skill 的触发优化建议、流程优化或优化 MR。SM 保留来源、归属、同步与应用状态等管理信息。

## 6. 初始化与本地运行节奏

用户体验目标是：拉下 SM 仓库，执行一个初始化命令，建立本机运行流程。

初始化命令负责检查运行条件，生成或安装当前用户的本地服务与定时执行配置。重复执行用于检查和补齐，不重复注册服务、采集 Hook 或定时任务。

服务首次启动时立即执行一次同步与应用：

1. 读取 SM 中的资源定义、来源和作用域。
2. 获取自建资源的已合并内容，跟随上游资源。
3. 根据 Agent、作用域和约定目录应用资源及相关配置。
4. 启用日常本地记录，并呈现本次执行结果。

日常使用期间轻量记录信息，把模型分析留到周期任务，避免拖慢用户工作。

周期任务默认安排在夜间，复用同步与应用逻辑，并处理尚未消化的本地记录：

- 同步并应用当前应使用的资源。
- 对自建资源的使用记录进行分析，提出有依据的改进尝试。
- 验证候选修改，形成规范 MR。
- 记录执行结果，供前端查看；合并内容在后续同步时应用。

具体夜间时刻、服务与调度实现由实现者采用简单方案确定并明确展示，不作为本轮产品选择题。

## 7. 使用记录与持续改进

记录服务于改进判断，需要能关联任务、项目、Agent 和被使用的自建资源，并保留足以复核的可见执行记录或本地引用。

采集应区分实际观察到的事实与推断。某类资源或 Agent 缺少可靠采集能力时，明确标记记录缺口，不把“没有记录”直接判成“未使用”。不要求采集模型未公开的内部推理。

### 触发、使用频率与淘汰

低频本身不是淘汰依据，需要结合适用任务判断：

- 很少出现适用任务：说明低频原因。
- 出现适用任务却未使用：检查是否可用、作用域是否正确，以及触发描述是否合适。
- 不合适的任务反而触发：检查描述和触发边界。
- 与其他自建资源重复或已被替代：提出合并、调整组织方式或淘汰的 MR。

### 执行后的反思

一次使用即可成为发现明确问题、提出改进的起点，不要求先积累固定次数。

例如，同一次任务中重复读取未变化的配置、重复查询已经确定的入口，可以作为冗余步骤的证据。分析应判断问题来自资源内容、Agent 的执行偏差，还是环境和输入，避免把所有问题都改进 Skill 文本。

候选改动需要说明问题、证据、拟采取的修改和影响范围，并对修改前后的结果进行可比较的验证。验证同时关注任务结果、必要步骤和效率，不能仅因步骤减少就宣称优化成功。

没有足够依据时保留观察结果，不为了满足每日产出而制造 MR。同一项已有待审提案应继续在该提案中处理，避免重复提交。

## 8. 优化 MR 的最低内容

| 内容 | 要求 |
| --- | --- |
| 问题与证据 | 哪些实际使用记录支持这次修改，哪些是推断 |
| 修改依据 | 问题属于哪个自建资源，为什么修改这里 |
| 修改内容 | 可审阅的内容差异，或组织、归属调整 |
| 对比验证 | 原有做法与修改后做法的结果、效率，以及未验证的情况 |
| 影响范围 | 涉及哪些资源、Agent 和用户／项目作用域 |

人工决定提案是否合理、是否需要进一步修改、是否合并。MR 提供可阅读的必要证据摘录和验证结果，便于审阅者判断。

## 9. 可视化管理

用户通过前端理解和管理资源，不依赖浏览仓库目录或直接阅读源文件来掌握整体情况。

前端需要可读地呈现资源用途、内容、来源、归属、适用 Agent，以及创建和修改所处的流程阶段。需要查看完整内容时，也有相应的阅读入口。

前端支持从不同问题进入同一套管理信息。首期视角建议如下，具体页面组织由实现者决定：

- 资源视角：有什么资源、作用是什么、由谁维护、在哪里使用。
- 作用域视角：用户级资源和各项目使用的资源。
- 使用与改进视角：自建资源的使用情况、发现的问题、证据和相关 MR。
- 本机运行视角：初始化、同步、应用、定时分析的执行结果，以及需要用户处理的情况。

这些视角能够相互关联，不分别维护互不一致的信息。多台机器各自本地运行和同步，不要求第一阶段另建一个集中管理所有用户或机器的平台。

## 10. 实现者采用的默认处理

以下是为避免在实现细节上反复提问而采用的默认值，不代表用户指定了技术方案：

- 复用本机已有的 Codex、Kimi、Git 和认证环境；初始化检查必要条件，缺项给出清楚提示。外部工具是否自动安装由实现时按最简单可行方案处理。
- 采用当前 Linux 用户的服务和调度能力，前端默认供本机访问。
- 不强制中断正在执行的 Agent 工作。分别呈现资源已应用到本地、Agent 是否需要在后续会话加载的情况，具体行为按实际接入能力核验。
- 认证凭据由本机提供，不作为资源内容提交到 Git；MR 提交必要的证据摘要，不默认提交完整会话或原始本地记录。
- 技术栈、元数据格式、界面布局、服务实现和分析器调用方式留给实现方案决定。需要改变已确认用户流程时再提出产品问题。

## 11. 第一阶段验收场景

| 编号 | 场景与可观察结果 |
| --- | --- |
| AC-01 | 在满足运行条件的 Linux 机器拉下 SM 后，一个初始化命令建立本地运行流程，首次同步与应用有明确结果；重复初始化不重复注册任务和 Hook。 |
| AC-02 | 一份自建资源在待审内容中修改后，本地生效位置仍保持已接受内容；MR 合并并完成下一次拉取应用后，生效位置才反映修改。 |
| AC-03 | 项目级资源只应用到声明归属的约定项目位置，不写入用户级位置；另一台采用相同目录约定的机器能够复用同一份归属信息。 |
| AC-04 | 自建资源的重命名、移动或删除审核合并后，在下一次应用时反映到受管理位置，旧受管副本不继续生效，无关本地内容保留。 |
| AC-05 | 上游资源定时获取并应用上游内容，普通更新不产生 SM 的审核 MR，也不进入自建资源的反思优化队列。 |
| AC-06 | 日常工作只进行轻量记录，不在用户任务中同步执行完整模型分析；记录覆盖不完整时前端明确说明。 |
| AC-07 | 对一条“遇到适用任务却未触发”的记录，分析能展示判断依据，检查可用性、作用域和描述，并将建议提交为待审核修改。 |
| AC-08 | 对包含两个有明确证据的冗余步骤的自建 Skill，一次使用后能形成有依据的修改提案，附修改前后验证结果，且不会自动应用待审改动。 |
| AC-09 | 夜间任务没有有效改进发现时不创建空洞 MR；已有同项待审 MR 时避免重复提出相同修改。 |
| AC-10 | 前端能阅读和定位五类资源，按来源、作用域、适用 Agent 查看，并关联使用证据、MR 和本机执行结果。 |
| AC-11 | 在另一台采用相同目录约定、满足运行条件的 Linux 机器上，经初始化恢复资源及应用配置，不要求用户逐个寻找和复制生效文件。 |
| AC-12 | 检查资源仓库和 MR 内容，不包含本机认证凭据；采集与加载能力未核验的部分不被报告为已验证成功。 |

实现验证的证据和未验证边界见[验证记录](../../verification.md)。
